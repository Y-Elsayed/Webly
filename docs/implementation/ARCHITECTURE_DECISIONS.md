# Pilot architecture and decision record

Decisions here select the smallest design that can satisfy the specification. They are proposals until implementation and pilot validation. Keep `webly.framework.build_pipelines`, file-backed local projects, and Streamlit usable; host mode may use separate adapters behind the same retrieval/ingestion contracts. Education rules are project configuration, never global behavior.

## AD-01 — Modular monolith and ownership

One FastAPI process owns admin/widget requests and a separate worker process consumes PostgreSQL-leased jobs/outbox items. PostgreSQL owns tenants, policies, source/version metadata, job states, conversation/feedback/contact records, usage ledger, analytics events and aggregates. Immutable content/index artifacts live in a local object-store-compatible directory for development and a managed object store for hosting. FAISS remains the vector engine. No graph DB, microservices, Redis, new vector backend or warehouse is justified. A PostgreSQL backed queue with `FOR UPDATE SKIP LOCKED`, lease expiry and idempotency avoids an additional broker at pilot volume. Operations must not use `webly/storage` file repository as the hosted authority.

## AD-02 — Canonical identity and evidence

Use opaque immutable `segment_id` (UUID or deterministic ID under a unique project/page-version/section/ordinal/chunker-version tuple); never use URL as a segment key. Each immutable snapshot manifest assigns unique signed 64-bit `vector_id` values and stores a bijection `vector_id → segment_id`, rejecting collisions and orphaned records. The retrieval DTO always has separate `segment_id`, `vector_id`, `page_version_id`, `section_id`, `source_id`, `original_text`, `embedding_text`, `url`, validity interval, and per-channel rank/score. BM25, planner actions, citations and trace/event IDs use `segment_id`. `original_text` and offsets are extracted before optional summary/contextualization; summaries are search aids only. Page content change creates a page version. Preserve exact source HTML and extraction/chunker versions. Old existing indexes with duplicate URL-derived IDs require complete re-embedding/rebuild from saved crawl HTML; if HTML is absent, recrawl under approved scope. Do not silently load legacy indexes into the hosted runtime.

## AD-03 — Immutable snapshot publication and request pinning

Build under a unique staging version. Persist source artifacts, metadata, lexical data and FAISS file; fsync/checksum for local storage or verify object store checksums; validate ID bijection, exact counts, dimensions, finite vectors, content provenance, embedding-space contract, source coverage, and quality gates. Mark the version `ready` in DB only after artifacts are durable. Publish with one DB compare-and-set transaction updating `project.active_index_version` from the expected predecessor and an outbox event. No query reads a directory being written. At request admission, read and pin active version plus policy/prompt version and load its immutable bundle into a bounded version-keyed cache; retain old bundle until pins drain. A process may race the DB pointer update: either old or new complete bundle is valid. Rollback is the same compare-and-set pointer operation to a retained validated version, subject to current critical-fact validity checks. Garbage collection never deletes a pinned version. A failure between artifact upload and DB commit leaves an unreferenced draft for cleanup; a DB commit must not precede artifact durability. Publication and rollback logs include actor, expected/current/new version. Local developer mode can use an atomic manifest pointer file with the same semantics without requiring PostgreSQL.

## AD-04 — Retrieval, facts and answer contract

Use vector + Unicode-aware lexical search over the pinned snapshot, fuse by canonical segment ID with reciprocal rank fusion (configurable `k=60`, one-based per-channel ranks), and select diverse evidence by subquestion coverage, redundancy and token budget. A URL may contribute several segments. Keep classic search as measured baseline. Builder gets at most one follow-up round and three unique searches by default; deterministic code checks schema, IDs, source/tenant validity, deadline, token/cost limit and action allowlist. `fetch_section`/neighbor lookups remain deferred unless corpus evaluation shows a gap they solve. Expose effective mode capabilities; a configured unsupported expansion is an error/visible warning, not a silent no-op. For institutional critical facts, approved structured fact rows have scope (program, campus, intake, year, language), source span, owner, effective/expiry and approval/version. Retrieval excludes expired or unapproved facts and checks conflicts; missing differentiating scope asks clarification. Conflicting approved facts block a concrete claim and create a review issue. Older source pages can remain stored for provenance while their expired facts are ineligible. Answer generation receives original spans with stable labels and structured fact constraints. Response schema includes status, citation IDs/spans, missing information and contact action. Citation membership/offset validation is automatic; semantic claim support still needs reviewed evaluation. One bounded repair then fallback. User conversation context can resolve references but is not institutional evidence.

## AD-05 — Delivery, idempotency and billing

The specification's “successfully delivered” is ambiguous under disconnect/retry. Proposed billable boundary: one unit for a unique accepted visitor request whose final structured response is durably committed to the request record and is successfully handed to the API transport for a nonstreaming response. A response can reach a socket but not a browser; the server cannot prove rendering. Therefore an uncertain disconnect after commit is marked `delivery_uncertain`, not silently double charged or declared viewed. Client retry with the same idempotency key retrieves the committed response for free, and customer-facing accounting defines that one unit remains chargeable unless operator reconciliation confirms failure to deliver. Disconnect before final response commit, provider failure, pause/quota fallback, staff preview and evaluation refund the reservation. Streaming is deferred for pilot unless a precise final delivery boundary and reconnect protocol is agreed. Store request ID, idempotency key, request hash, reservation/final state, pricing version, attempt cost, response hash, delivery state, timestamps in one transactional ledger. Duplicate keys with different payloads conflict. Reserve with row lock/unique constraint against period allowance; finalize/refund once with atomic transitions; timeout sweeper reconciles abandoned reservations against committed response records. Planner calls and retries accrue internal cost but not extra question units. Browser events never authorize charges. Expose pending/uncertain counts and a reconciliation report. Publish this contract before billing; customer must approve the ambiguity policy.

## AD-06 — Analytics and privacy semantics

Domain transaction writes an outbox event with unique event ID; worker inserts into deduplicated event table and recomputes affected project-local reporting days using `event_time_utc`, not processing time. Keep `ingested_at_utc` and dashboard processing watermark/lag. Unique constraints prevent replay inflation. For arbitrary date windows, query distinct conversation/session IDs from filtered rows; do not sum daily distinct counts. Every rate exposes numerator, denominator, definition version and `not enough data` for zero denominator. `origin` is server assigned for authoritative events (visitor, staff preview, evaluation, monitor); client impressions/clicks are untrusted observations. `answer_delivered` follows the billing delivery contract and remains distinct from `contact_submitted`, `contact_delivery_updated`, human `conversion_confirmed`, and reviewed `resolution_confirmed`. Feedback is one current rating per turn with replacement history/audit; negative feedback and sampled positives enter review. Raw/redacted transcripts and contact PII stay in restricted tables, never generic event properties. Tenant/project/timezone/index/prompt/policy/version filters are mandatory on reporting. Corrections to late events rebuild affected aggregates and report processing watermark. Billing ledger remains authoritative if analytics is down. Proposed retention defaults from spec require customer agreement; deletion tombstones propagate to transcript excerpts, review issues, search/export material and are replayed before serving restored backups. Aggregates may remain only if nonidentifying under agreed policy. Backups have expiry, encryption and tested restore.

## AD-07 — Hosted boundary and crawler

Admin uses a configured hosted identity provider and server-side tenant membership/role checks; explicit project ownership and composite tenant/project foreign keys defend against mixups. Public widget gets a short-lived project-scoped anonymous session token; approved origins, CAPTCHA/rate limits and signed project keys reduce abuse, but origin headers do not authenticate users. Visitor text size, query cost and concurrency are bounded. Crawling is restricted to approved public HTML in R1. Resolve DNS for each request/redirect/robots fetch; reject non-HTTP(S), credentials in URL, forbidden ports and private/link-local/loopback/metadata ranges, and bind connection to validated destination to prevent DNS rebinding. Disable automatic redirects and validate every hop; stream response bytes with actual cap, not only `Content-Length`; block egress to internal networks at deployment. Domain/path/robots/page/depth/time limits and explicit exclusions remain. The current Atlas fetch path must be wrapped or patched at the transport boundary; validating only the starting URL is insufficient. No general arbitrary URL fetch tool is exposed to the planner.

## AD-08 — Compatibility and scope challenge

The spec's proposed endpoints are new hosted contracts. Preserve existing local `/v1/projects/{name}` API only for local mode or introduce explicit versioned migration/deprecation; do not change `QueryResult` fields without adapting local callers/tests. Current `summary_model` defaults empty, so evidence loss affects summary-enabled projects, not every default project. Arabic lexical/RTL gates apply only if Arabic is sold. `fetch_neighbors`, `fetch_section`, direct graph lookup, incremental embeddings, automated clusters/digests, streaming, self-service subscriptions, CRM, PDFs and student records are deferred. A manual weekly managed-pilot report satisfies the review intent until opt-in digest automation is needed. The detailed 7-role matrix can be implemented using role permissions plus a support assignment relation; avoid building a general policy engine. Use actual workload measurements before building a precomputed lexical index or replacing FAISS. Admission-specific structured facts are necessary when fee/deadline/eligibility claims are allowed; a general support pilot can launch without them if policy forbids those claims.

## Decisions requiring owner/customer input

Choose first pilot/customer and source approver; decide Arabic and admissions scope; approve public HTML/editor answers as initial sources; define critical fact owner/expiry and whether a human can staff contact inbox; confirm retention/export and accepted visitor fields; decide billing allowance and `delivery_uncertain` handling; provide nonproduction identity/provider/object-store credentials and hosted network controls; approve human-reviewed evaluation corpus and paid model-call budget. These are external prerequisites, not facts to infer from the repository.

## R0 implementation record (2026-10-17)

- AD-02: deterministic SHA-256 segment IDs cover page URL + original HTML version, global chunk index, chunk identity, embedding-part index and `chunker-v2`. FAISS IDs are checked signed 64-bit hashes of those IDs. The saved record keeps both `original_text` and `embedding_text`; citations use original spans. The existing `SourceRef.chunk_id` field is retained for local callers but contains the canonical segment ID. Legacy indexes are rejected and require a rebuild from original HTML, not an in-place relabel.
- AD-03: local mode uses `filelock` for one project ingest and pointer publication, immutable version directories, fsynced artifacts, SHA-256 checksums, an atomic active pointer with compare-and-set, and explicit rollback. Each `ProjectRuntime` swaps and validates a complete bundle under a reentrant query lock; independent runtimes pin their own loaded bundle. No GC is implemented, so old versions remain safe for pins at the cost of disk use. PostgreSQL/outbox/object-store publication and policy/prompt pins remain R1, not smuggled into R0.
- AD-04: RRF fuses semantic and lexical hits by segment, including multiple segments on a page; Arabic Unicode words survive lexical tokenization. Builder follow-ups are capped at three unique queries overall and one round by default; classic rewrites are capped at three searches. Prompt preflight uses UTF-8 byte length as a conservative token upper bound plus output reserve without a network tokenizer. Generated responses must use structured status and exact original spans in the supplied context; one repair is allowed, then fail closed. Exact-span validation is not semantic support evaluation. A memory-only transform remains usable locally but is explicitly `unverified_transformation`, never a grounded answer.
- The R0 artifact manifest format is 1 while the internal FAISS metadata format is 2; these are distinct version numbers. This avoids conflating snapshot-container changes with vector-record schema changes. Embedding-space compatibility includes model, dimension, normalized-IP metric and chunker version. Direct low-level `FaissDatabase.save()` remains available for isolated/local library usage, but project ingestion always publishes via the snapshot store.
- Deviations from T01/T02 task sketches: R0 keeps the existing dictionary-based public search DTO and validates canonical fields at FAISS/retrieval boundaries, instead of introducing a broad typed DTO rewrite. The existing local `index_only` ingest API is the rebuild operation, documented in `R0_RUNBOOK.md`, instead of a second migration CLI. Both choices preserve framework compatibility and avoid duplicate paths; neither attempts to reuse legacy ambiguous vectors.
